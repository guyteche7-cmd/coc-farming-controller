# Clash of Clans Autonomous Farming Controller
# Project Codebase Knowledge

## 1. Project Overview
The `coc-farming-controller` is an autonomous AI-driven script/bot designed to automate resource farming in the game Clash of Clans via Android emulators (like LDPlayer or BlueStacks) on Windows. 

The primary purpose of the project is to read the screen state of the game, automatically search for multiplayer battles or Builder Base matches, deploy troops/heroes using predefined algorithms, and monitor the battle to completion before repeating the cycle. 

The project is divided into two major subsystems:
1. **Main Village Farming (`src/`)**: Handles multiplayer matchmaking, loot OCR (reading gold, elixir, dark elixir), wall upgrading, and complex army deployment (spells, heroes, troops).
2. **Builder Base Farming (`builderBase/`)**: Handles the two-stage Builder Base battles, rapid deployment, and simplified looping without loot requirements.

**Execution Flow**:
The user launches the bot either via a CLI entry point or a GUI dashboard. The bot binds to the emulator window using Windows APIs (`ctypes`), calibrates the screen coordinate system, and starts a background worker thread (`SessionController`). This thread runs a State Machine that continuously takes screenshots, passes them to a Vision pipeline (Template Matching + OCR + YOLO object detection), determines the `UIState`, and uses Planners to generate simulated mouse clicks executed by an `InputAdapter`.

## 3. File-by-File Detailed Analysis

### `src/control/state_machine.py`
**Responsibility**: Executes the Main Village state transition loop.
**Key Functions**:
- `step()`: Called repeatedly by the session controller. Captures a screenshot, detects state via `UIStateDetector`, and delegates to `_handle_X()` methods.
- `_handle_home()`: Clicks "Attack". Checks if the army is ready.
- `_handle_attack_menu()`: Clicks "Find Match".
- `_handle_searching()`: Runs Loot OCR. Passes loot to `TargetEvaluator`. If pass -> transitions to Deploy. If fail -> clicks "Next".
- `_handle_battle()`: If not deployed, runs `DeploymentPlanner`. If deployed, uses `BattleDetector` to monitor combat progress and `ExitEvaluator` to click "Surrender" or wait.

### `builderBase/src/bb_state_machine.py`
**Responsibility**: Executes the Builder Base state transition loop.
**Key Functions**:
- `step()`: Similar to main village, but relies on `BBStateDetector`.
- `_handle_home_state()`: Checks if the attack quota is met, otherwise clicks Attack.
- `_handle_stage1_battle()`: Waits exactly 6.0 seconds to allow the map to settle, then deploys troops by calling `BBDeploymentPlanner`.
- `_handle_stage2_battle()`: Re-deploys remaining troops in the second map.

### `src/planning/deployment_planner.py`
**Responsibility**: Mapping conceptual army lists into screen pixel clicks.
**Logic**: Receives a normalized play area. Calculates linear anchor points along an edge (Top/Bottom/Left/Right). Yields a list of `Action` objects (Click X,Y -> Wait 0.2s -> Click X2,Y2).
**Side Effects**: None directly. It returns a plan. The `ActionExecutor` actually clicks.

### `src/control/input_adapter.py`
**Responsibility**: Direct OS integration.
**Logic**: Contains `RealInputExecutor`. Uses `ctypes.windll.user32.SendInput` or `win32api` to send hardware-level mouse down/up events to a specific HWND window. Essential for bypassing emulator anti-macro measures.

## 4. Function and Class Inventory

- **Class**: `SessionController` (in `src/control/session_controller.py`)
  - **Purpose**: Threads the execution.
  - **Inputs**: `ConfigManager`
  - **Important Logic**: Uses a `while self.is_running:` loop inside a daemon thread. Catches all exceptions to prevent crashes.
- **Class**: `UIStateDetector` (in `src/vision/state_detector.py`)
  - **Purpose**: Identifies the screen state.
  - **Logic**: Performs `cv2.matchTemplate` against predefined assets (`assets/ui/`). Returns an Enum like `UIState.HOME` or `UIState.SEARCHING_OPPONENTS`.
- **Class**: `ExpressionEvaluator` (in `src/rules/expression_parser.py`)
  - **Purpose**: Safe boolean parsing.
  - **Logic**: Uses Python's `ast` module to safely compile target logic like `gold > 1000000` into executable functions without using `eval()`.

## 5. Execution Flow

**Startup**:
1. User runs `main.py --cli` or `gui_app.py`.
2. `ConfigManager` loads `config.yaml`.
3. `SessionController` (or `BBSessionController`) is initialized.
4. User presses the Start Hotkey (or GUI button).
5. Controller finds the Emulator Window handle (HWND) using `win32gui.FindWindow`.
6. Calibrates the Viewport (finds the actual rendering space inside the emulator window borders).
7. Spawns the `Worker Thread`.

**Main Loop (Worker Thread)**:
1. Capture Screenshot via `ScreenCapture` (using `mss` or `win32gui` bitblt).
2. Pass image to `StateMachine.step()`.
3. `StateDetector` crops specific ROI (Regions of Interest) and does Template Matching.
4. Based on the state, run logic (OCR, Planning, etc).
5. Generate a sequence of Clicks.
6. `ActionExecutor` maps normalized clicks `(0.5, 0.5)` to physical pixels and executes `SendInput`.
7. Loop repeats every ~0.5 to 1.0 seconds.

**Shutdown**:
1. User presses Stop Hotkey.
2. `is_running` set to `False`. Thread joins.

## 12. Error Handling and Recovery

- **SessionController Thread**: Enclosed in a massive `try/except Exception`. If an error occurs, it is logged and the session stops to prevent rogue clicks.
- **Vision Fallbacks**: If OCR fails or returns gibberish, `LootDetector` returns 0. The bot assumes a bad base and skips.
- **Recovery**: If the bot gets stuck in an unrecognized UI state for too long (e.g., popup ad, disconnected), the state machine currently logs `UNKNOWN` state and idles. *There is limited active automatic app-restarting recovery.*

---

## 13. Important Algorithms and Logic

- **Template Matching**: Uses `cv2.matchTemplate(image, template, cv2.TM_CCOEFF_NORMED)`. Checks if `max_val > 0.8`.
- **Dynamic Scaling**: The detectors dynamically scale templates based on the emulator's current height compared to a baseline 1080p height (`scale = fh / 1080.0`).
- **Deployment Line**: Calculates vector points between two screen coordinates. `Deploy step = (End - Start) / TroopCount`. Uses `time.sleep(tap_delay)` between clicks.

## 14. State Machines / Modes / Workflows

**Main Village States** (`UIState`):
- `HOME`: Idle on base.
- `ATTACK_MENU`: The multiplayer selection screen.
- `SEARCHING_OPPONENTS`: Clouds.
- `ENEMY_BASE_REVEALED`: Base is visible, loot can be read.
- `ACTIVE_BATTLE`: Troops have been deployed.
- `BATTLE_RESULT`: Win/Loss screen showing loot gained.

**Builder Base States** (`BBUIState`):
- `BB_HOME` -> `BB_START_ATTACK_MODAL` -> `BB_SEARCHING` -> `BB_BATTLE_COUNTDOWN` -> `BB_STAGE1_BATTLE` -> `BB_STAGE2_BATTLE` -> `BB_RESULT_SCREEN`.

---

## 15. Threads, Async, Timing, and Concurrency

- **Main Thread**: Runs the `CustomTkinter` GUI event loop.
- **Worker Thread**: The `SessionController` runs in a `threading.Thread(daemon=True)`.
- **Concurrency Issue**: The worker thread uses `time.sleep()` heavily. This is blocking, but since it's on a background thread, the GUI remains responsive.
- **Safety**: `ctypes` mouse movements are technically global OS events. If the user moves the mouse physically, it races against the bot's programmatic clicks.

## 17. Important Assumptions

- **Resolution Assumption**: The emulator is assumed to be running in 16:9 aspect ratio (ideally 1920x1080). While dynamic scaling exists, extreme aspect ratios will break UI anchor math.
- **UI Scaling**: Assumes in-game UI scaling is standard.
- **Window Title**: Assumes emulator window titles match the regex (`Google Play Games|Clash of Clans|BlueStacks|LDPlayer`).
- **Focus**: Assumes it can successfully steal focus to the emulator before clicking.

---

## 18. Known Problems / Risks / Suspicious Areas

- **POSSIBLE ISSUE - Screen Focus Racing**: The bot steals window focus to click. If the user clicks elsewhere mid-deployment, the bot will click the desktop, causing chaos.
- **TECHNICAL DEBT - OCR Engine**: Tesseract is famously brittle on varied backgrounds. The `test_loot_ocr.py` tool shows varying success rates depending on base background color.
- **TECHNICAL DEBT - Error Recovery**: If the game crashes, the bot gets stuck in `UNKNOWN` state forever instead of rebooting the emulator.

---

## 19. Important Relationships and Coupling

- **`ActionExecutor` & `ViewportCalibrator`**: Highly coupled. `ActionExecutor` requires perfect offsets from `ViewportCalibrator`. If the window borders (e.g., LDPlayer title bar) change size, all clicks are offset by Y pixels.
- **Template Images & Code**: Code relies on filenames inside `assets/ui/`. If an asset is deleted, the bot will crash unless graceful fallback is coded.

---

## 20. Safe Modification Boundaries

- **Safe to Modify**: `tools/` scripts, `rules/expression_parser.py`, `planning/deployment_planner.py` (assuming the API footprint doesn't change).
- **Dangerous to Modify**: `capture/screen_capture.py` and `calibration/viewport.py`. Changes here break the coordinate systems for the entire application.

## 22. Critical Code Paths

**Normal Attack Flow (Main Village)**:
1. `SessionController` loop calls `StateMachine.step()`.
2. `UIStateDetector` returns `UIState.ENEMY_BASE_REVEALED`.
3. `LootDetector` scans Gold/Elixir.
4. `TargetEvaluator` checks logic (`gold > 1000000`).
5. Evaluator returns `True`.
6. `DeploymentPlanner` generates edge-based click sequence.
7. `ActionExecutor` executes clicks.
8. State transitions to `ACTIVE_BATTLE`.
9. `BattleDetector` waits for damage % to freeze or troops to die.
10. `ExitEvaluator` triggers Surrender click.

## 23. Glossary

- **Normalized Coordinates**: `(0.5, 0.5)` represents the exact center of the emulator viewport regardless of actual resolution.
- **Viewport**: The actual pixel area displaying the game, excluding emulator title bars and sidebars.
- **Pill**: The small oval buttons in Builder Base (e.g., "Boost Army", "Surrender").
